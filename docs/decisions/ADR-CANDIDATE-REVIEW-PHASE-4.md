## 1. Overall Recommendation
The proposed candidate Architectural Decision Records (ADRs) for Phase 4 (Local AI Input Pipeline and Prediction Engine Planning) are highly aligned with the project's governance limits and structural isolation policies.

## 3. Per-ADR Explanation & Findings

### ADR-0017: Local AI Input Candidate Boundary
* **Classification**: `READY_FOR_DRAFT_AND_ACCEPTANCE`
* **Findings**: Safe. The use of generic input candidates derived from Phase 3 contracts decouples preprocessing from sports API vendors.
* **Additional Note**: Input candidates are not predictions and must not contain owner-undecided model features, weights, betting signals, or strategy decisions.

### ADR-0018: Prediction Output Envelope and Trace Contract
* **Classification**: `READY_FOR_DRAFT_AND_ACCEPTANCE`
* **Findings**: Safe and necessary. Standardizes predicted outcome envelopes with audit traces for debugging and traceability. No probability or confidence formulas are defined.
* **Additional Note**: Outcome labels, recommended bets, stake fields, confidence percentages, or probability fields require later owner-approved ADRs before implementation.

### ADR-0019: Prediction Engine Runtime and Algorithm Selection Boundary
* **Classification**: `READY_WITH_MINOR_REVISION`
* **Findings**: Safe to defer final model selection. Scaffolding a mock prediction engine is allowed to verify integration channels.
* **Revision Requirement**: Revise wording to ensure the mock engine returns traceable mock envelopes only and does not return real outcome predictions.

### ADR-0020: LLM Explanation Role and Prediction Refusal Boundary
* **Classification**: `READY_FOR_DRAFT_AND_ACCEPTANCE`
* **Findings**: Safe. Restricting the LLM to explaining pre-calculated prediction envelopes ensures that the LLM does not speculate or hallucinate results. Refusal criteria are well-formulated.
* **Additional Note**: Natural language explanations generated by the LLM must reference the associated `predictionId` or `traceId` when available.

### ADR-0021: Prediction Evaluation and Backtesting Boundary
* **Classification**: `READY_WITH_MINOR_REVISION`
* **Findings**: Safe. Planning a test harness structure for backtesting avoids implementing betting wagers or ROI analysis.
* **Revision Requirement**: Revise wording to restrict metrics to candidate discussions only and explicitly forbid bankroll, ROI, or stake-based evaluations.

## 4. Required Wording Fixes

### ADR-0019 Wording Revision
We must include this text in the Recommended Direction:
> "Phase 4 may implement a mock prediction engine that returns traceable mock envelopes only. It must not return real outcome predictions, betting picks, probability percentages, or confidence scores. The safest default is `predictionAvailable: false` or `engineMode: mock`."

### ADR-0021 Wording Revision
We must include this text in the Recommended Direction:
> "Candidate metrics may be listed for discussion only, such as accuracy-like counts, coverage, calibration notes, or trace completeness. No metric is final, no threshold is accepted, and no betting ROI, bankroll, or stake-based evaluation is authorized in Phase 4."
