# ADR-0003 Phase 2 Owner Review: Product Boundary Gateway

This document serves as the decision gateway for [ADR-0003-product-boundary-first-planning-target-draft.md](file:///c:/CODE/miraichi/docs/decisions/ADR-0003-product-boundary-first-planning-target-draft.md) at the start of Phase 2 (App Skeleton and Scaffold Planning).

## The Decision

Decide on the scope of the first product milestone to determine which routes, UI layouts, and API/worker communication stubs are created during Phase 2 scaffolding.

## Options for the First Milestone Boundary

### Option A: Prediction Review and Explanation Only
* **Scope**: The client application allows users to view a list of upcoming matches, view predictions generated by the local AI, and interact with the LLM chatbot to ask for explanations of those predictions.
* **Pros**: Simplest possible boundary; no betting concepts are introduced in the front-end or API models yet.
* **Cons**: Scaffolding will completely omit betting layouts, making future introduction of bet history harder to refactor.

### Option B: Prediction Review, Explanation, and Read-Only Bet History Placeholders (Recommended)
* **Scope**: In addition to Option A, the web application includes UI placeholders (e.g., a "Bet History" tab or log view) displaying mock bet audit records. The API supports fetching mock/read-only bet logs.
* **Pros**: Allows scaffolding the complete client navigation structure and backend API schemas for audit trails without implementing any betting logic, bankroll tracking, or risk calculations.
* **Cons**: Introduces additional API endpoints and client components that remain mock-only in Phase 2.

### Option C: Full Betting Management Surface
* **Scope**: Includes predictions, LLM explanations, active bet slip placement, live bankroll balances, risk-limit validations, and real-time accuracy calculations.
* **Pros**: Delivers the full feature set immediately.
* **Cons**: Violates the Phase 2 scaffolding boundary by forcing database schemas, bankroll persistence, and mathematical logic into the code way before data ingestion (Phase 3) or local AI pipelines (Phase 4) are ready.

---

## Technical Recommendation & Owner Decision

**Option B (Prediction review, explanation, and read-only bet history placeholders)** is **Approved by Project Owner** on 2026-06-23. 

* **Option A**: Superseded by Option B.
* **Option C**: **Rejected** for Phase 2. No live betting calculations, risk management, or active bet slips will be scaffolded.

### Rationale
1. **Scaffold Completeness**: It allows the developer to construct a realistic client-server skeleton that covers the entire main user journey (view prediction -> request explanation -> log simulated bet/history).
2. **Boundary Safety**: It introduces the data model requirements for bet history early without implementing any high-risk betting calculations or production schemas, conforming to the project plan's safety guardrails.
3. **No Lock-In**: Keeps actual bankroll rules and risk calculators deferred while exposing where those hooks will live in the UI/UX.

---

## Scaffolding Boundary Note

All betting-related components, models, and endpoints created in Phase 2 are strictly placeholder-only, mock-driven, and client-side stubs. No real bet persistence, active bet placement, bankroll tracking, or risk math is authorized or implemented.
